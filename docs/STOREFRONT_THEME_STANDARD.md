# 前台主题标准（前后端解耦）

> 状态：标准草案，待确认。日期：2026-11-14
> 目标是对齐 Shopify 主题的做法：后端负责业务和数据，前台主题只负责视觉，可以整套替换。
> 本文**不**要求现在开发第二套 UI，只定义任何主题都必须遵守的边界、必须具备的能力，以及验证方法。

## 1. 原则

1. **业务只在后端。** 价格、折扣、库存、钱包、佣金、支付状态都以服务端为准。主题可以显示预估值，但必须调用标准 SDK 里的同一份计算规则，不能自己重写一套。
2. **主题只做视觉。** 一个主题 = 页面模板 + 组件 + 设计令牌（颜色、字体、圆角等）+ 文案键。主题不直接写 SQL，也不调后台（`/api/admin/*`）接口。
3. **能力对齐。** 每个主题都必须覆盖第 4 节列出的全部能力。新增一项前台能力时，先补进能力清单和 SDK，再由各主题实现；能力不能只在某一套主题里存在。
4. **结账归平台所有。** 和 Shopify 一样，结账、支付回调和订单结果页的逻辑由平台统一提供，主题只能换外观（样式和文案），不能改流程和金额计算。

## 2. 分层

```
┌──────────── 主题（可替换）────────────┐
│ 模板 templates/   组件 sections/   令牌 tokens.css   theme.json │
└───────────────┬─────────────────────┘
                │ 只依赖下面这一层
┌───────────── 前台 SDK（平台提供，稳定）─────────────┐
│ 数据：useProducts / useProduct / useCart / useSession / useAccount ... │
│ 动作：addToCart / placeOrder / applyCoupon / submitReview ...           │
│ 规则：money-rules（预估折扣、钱包份额）、格式化、i18n、货币            │
└───────────────┬─────────────────────┘
                │ HTTP，带登录凭证
┌────────── 前台接口（Commerce API，版本化）──────────┐
│ /api/products /api/orders /api/memberships/me /api/wallet /api/affiliates ... │
└──────────────────────────────────────────────┘
```

- **前台接口：** 现有的 `/api/*`（不含 `admin`、`pos`、`cron`、`debug`）。按资源整理成文档，带版本号；返回结构的变更必须向后兼容。
- **前台 SDK：** 新建 `src/storefront/sdk/`，封装全部数据获取和动作。它统一负责带登录凭证（`apiFetch`）、错误码翻译和演示模式。主题里不允许直接写 `fetch("/api/...")`。
- **主题：** `src/themes/<name>/`，只能依赖 SDK、UI 基础组件和 i18n。

## 3. 主题包结构

```
src/themes/<name>/
  theme.json        # 名称、版本、支持的模板列表、可配置项（schema）、默认值
  tokens.css        # 设计令牌，全部是 CSS 变量；明暗两套
  templates/        # 每个页面类型一个模板（见 4.1）
  sections/         # 主题自己的区块组件
  locales/          # 只放主题特有的文案键；通用文案用平台词条
```

- 当前主题在后台设置里选择（沿用 `site_settings.site.theme`），`?theme=` 只用于预览。
- 主题的可配置项（横幅图片、标题、首页区块顺序等）按 `theme.json` 里的 schema 存在 `site_settings`，后台根据 schema 自动生成表单。这就是以后做「主题编辑器」的基础，但不在本标准的第一阶段范围内。

## 4. 能力清单（每个主题必须全部实现）

### 4.1 页面类型（模板）

| 模板 | 路由 | 必须支持的能力 |
|---|---|---|
| home | `/` | 商品推荐位、分类入口、配置化区块 |
| collection | `/products`、分类页 | 筛选、排序、分页、加购；有规格或多种配送方式时引导去详情页 |
| product | `/products/[id]` | 规格选择、配送方式、库存、价格区间、图集、评价（查看与提交）、心愿单、对比、推荐、WhatsApp 咨询 |
| search | 命令面板 / 搜索页 | 关键字搜索商品 |
| cart | `/cart`、购物车抽屉 | 增删改数量、小计、运费提示 |
| account | `/account` | 资料、会员等级与折扣、钱包余额与到期、优惠券、地址 |
| orders | `/orders`、`/orders/[id]` | 订单列表、详情、时间线、申请退款 |
| auth | 登录、注册、找回、重置密码 | 邮箱登录、第三方登录、注册流程 |
| affiliate | 申请、面板、提现 | 推广链接、佣金记录（含退款扣回）、提现条件与进度、申请提现 |
| static | 关于、联系、配送说明 | 内容来自设置或 CMS |
| 404 / 错误页 | — | 本地化文案 |
| layout | 页头、页脚 | 导航、语言、货币、主题切换、购物车数量、登录状态 |

结账（`/checkout`、`/checkout/success`）是平台模板：主题只能提供样式覆盖。

### 4.2 横向要求

- **多语言：** 中、英、葡三种语言全部有文案；不允许硬编码文字，i18n 门禁新增必须为 0。
- **多币种：** 金额一律经过货币格式化，不写死 `$`。
- **会员、钱包、佣金：** 开关关闭时不显示相关入口；开启时显示并遵守有效期。
- **登录凭证：** 一律经 SDK 发请求。本次点测发现推广提现页、申请页和商品评价提交都直接用了 `fetch`，导致请求 401，已修复。这条就是为了防止此类问题再次出现。
- **可访问性与响应式：** 375 px 手机宽度可用；关键操作可用键盘完成。
- **演示模式：** 只在 SDK 和服务端处理，主题里不出现演示数据或演示账号。

## 5. 验证（主题的「合格证」）

1. **能力清单自检：** `theme.json` 声明已实现的模板；脚本检查是否覆盖 4.1 的全部模板，缺一个就构建失败。
2. **静态门禁：** 主题目录里禁止出现 `fetch(`、`/api/admin`、数据库导入和硬编码文字（扩展现有 i18n 门禁和 lint 规则）。
3. **端到端冒烟：** 同一套 Playwright 用例对每个已安装主题各跑一遍，至少覆盖：浏览 → 加购 → 结账（线下支付）→ 订单详情 → 账户页 → 推广面板。用例只依赖 `data-testid` 和 SDK 的行为，不依赖具体视觉。

## 6. 现状差距

| 标准要求 | 现状 |
|---|---|
| 主题只依赖 SDK | 15 个前台页面自己调接口；部分用 `fetch`、部分用 `apiFetch` |
| 主题覆盖全部模板 | 两套主题只覆盖首页、页头、页脚；其余页面两套共用 |
| 不在主题里放演示逻辑 | 演示数据在服务层，登录页和结账页的演示提示已改为由服务端判断 |
| 金额规则只有一份 | 结账页的预估已经复用 `money-rules`，符合要求 |
| 文案全部走词条 | 已满足（i18n 门禁为 0） |

## 7. 落地步骤（不新增 UI）

1. **定义接口与 SDK：** 整理前台接口文档；建 `src/storefront/sdk/`，把现有页面里的数据获取和动作迁过去。页面外观不变。
2. **主题目录与清单：** 把现有两套首页、页头、页脚迁到 `src/themes/tech`、`src/themes/shopify`，加上 `theme.json`；其余页面先作为两套主题共用的「基础模板」。
3. **门禁与冒烟：** 加入第 5 节的三项验证，接进 CI。

完成后，开发新主题只需要按清单实现模板，平台侧的能力和验证都是现成的。主题编辑器（后台拖动区块、改设置、预览发布）可以以后在 `theme.json` 的 schema 上再做。
